# 大模型安全创新比赛实施建议与落地路线

## 1. 项目定位

建议将当前项目定位为：

> 面向真实大模型应用链路的自适应红队评测与防护闭环平台。

不要把比赛主线扩散成“大模型全生命周期安全平台”“多模态伪造检测平台”或“联邦学习隐私保护平台”。这些方向虽然宏大，但与当前工程的题库、越狱评测、模型评估、报告生成等基础能力结合不够紧，短期内难以形成稳定可演示的创新闭环。

当前项目最适合强调：

1. 从单轮问答评测扩展到 RAG、Agent、多轮上下文等真实应用链路。
2. 从固定题库和固定模板扩展到基于历史反馈的自适应红队攻击。
3. 从风险分数展示扩展到风险来源定位、证据链解释和防护建议生成。
4. 从一次性评测扩展到修复后的回归验证和安全漂移监测。

一句话包装：

> 本项目不是单纯测模型会不会越狱，而是面向 RAG 和 Agent 真实应用链路，自动生成攻击、定位风险来源、推荐防护策略，并通过回归测试量化修复效果的大模型应用安全闭环平台。

## 3. 核心创新点建议

### 创新点一：链路级 Trace 安全归因

#### 目标

将评测对象从“用户问模型一个问题，模型给一个回答”扩展为完整应用链路：

```text
用户输入 -> 检索请求 -> 文档召回 -> 上下文拼接 -> 模型生成 -> 工具调用 -> 后处理审查 -> 最终输出
```

平台不仅给出风险分数，还要回答：

- 风险发生在哪个环节？
- 是用户输入诱导、检索文档污染、系统提示泄露，还是工具调用越权？
- 哪一段证据支持这个判断？
- 应该在哪一层加防护？

#### 可实现功能

1. 记录每次应用调用的 Trace。
2. 将 Trace 拆成多个 Step，例如 `user_input`、`retrieval`、`context_build`、`model_output`、`tool_call`、`post_check`。
3. 对每个 Step 标注风险类型、风险等级、证据片段。
4. 在前端用时间线或链路图展示风险传播路径。

## 4. 创新点二：轻量自适应红队策略调度

### 目标

将当前固定越狱变形方法升级为“基于反馈的自适应红队引擎”。

当前已有策略：

- 逻辑诉求变形
- 权威说服变形
- 角色扮演变形
- 情景引导变形
- 过去式攻击变形
- 截断诱导变形

建议新增策略：

- 多轮上下文诱导
- many-shot 长上下文攻击
- 间接提示注入
- RAG 污染攻击
- Agent 工具越权诱导
- 编码/混淆绕过
- 系统提示词泄露诱导

### 不建议直接做复杂强化学习

比赛阶段不建议从零实现复杂强化学习。可以先做轻量策略调度器：

```text
策略得分 = 历史成功率 * 0.45 + 平均风险分 * 0.35 + 新颖度 * 0.10 - 平均成本 * 0.10
```

每轮攻击后记录：

- 使用了哪个策略。
- 对哪个风险类别测试。
- 模型是否拒答。
- 是否出现危险输出。
- JudgeService 给出的分数。
- 是否触发目标风险。
- token 成本和耗时。

下一轮根据策略得分选择更可能成功的策略。

## 5. 创新点三：RAG 污染评测沙箱

### 目标

构建一个可控 RAG 安全评测环境，模拟真实知识库问答中的风险：

- 恶意文档注入。
- 检索内容劫持。
- 私有文档越权召回。
- 引用不可信来源。
- 污染文档影响最终答案。

### 为什么值得做

RAG 是当前大模型应用最常见的落地方式之一。传统越狱测试主要测模型本身，而 RAG 风险来自知识库、召回机制和上下文拼接，更贴近企业真实场景。

PoisonedRAG 相关研究已经证明，向知识库注入少量恶意文本即可操控 RAG 输出。这非常适合作为比赛中的“新型风险场景”。

### 最小可实现版本

不必一开始接复杂向量数据库。建议先做轻量沙箱：

1. 用数据库表保存文档。
2. 用简单 embedding 或关键词相似度做检索。
3. 每个文档带上：
   - 文档可信等级。
   - 所属租户或权限范围。
   - 是否污染文档。
   - 是否包含注入指令。
4. 构造 RAG prompt。
5. 调用目标模型。
6. JudgeService 判断模型是否采纳污染内容。

## 6. 创新点四：Agent 工具越权评测沙箱

### 目标

评测大模型 Agent 在工具调用场景下是否存在：

- 工具越权调用。
- 危险参数生成。
- 未经确认执行高危操作。
- 被外部内容诱导执行攻击者任务。
- 泄露工具返回的敏感信息。

### 最小可实现版本

不接真实危险工具，只做模拟工具：

- `search_docs`
- `query_user_profile`
- `send_email_mock`
- `delete_file_mock`
- `payment_mock`
- `update_project_config_mock`

每个工具定义：

- 权限等级。
- 是否高危。
- 参数 schema。
- 是否需要二次确认。
- 允许访问的数据范围。

## 7. 创新点五：防护建议与一键回归验证

### 目标

让平台从“发现风险”变成“治理风险”：

```text
发现风险 -> 定位风险来源 -> 生成防护建议 -> 应用/记录修复方案 -> 回归验证 -> 报告对比
```

### 防护建议类型

建议先覆盖以下几类：

1. 提示词加固：
   - 系统 Prompt 增加边界说明。
   - 明确不信任外部文档中的指令。
   - 要求区分用户指令、系统指令、检索内容。

2. 输入过滤：
   - 检测越狱关键词。
   - 检测编码混淆。
   - 检测间接提示注入模式。

3. 检索防护：
   - 文档可信等级过滤。
   - 多租户知识库隔离。
   - 检索内容注入指令检测。
   - 引用来源校验。

4. 工具权限控制：
   - 工具白名单。
   - 参数 schema 校验。
   - 高危工具二次确认。
   - 最小权限原则。

5. 输出审查：
   - 敏感信息脱敏。
   - 有害内容分类。
   - 系统提示词泄露检测。

1. `TraceRisk` 生成后，根据 `risk_code + scenario_type + step_type` 查询 `MitigationTemplate`。
2. 如果有模板，生成稳定建议。
3. 如果需要更自然的报告表达，再调用 LLM 润色，但结构字段必须来自模板。
4. 将失败样例写入 `RegressionSet`。
5. 用户点击“一键回归验证”，创建 `EvaluationRun(run_type="regression")`。
6. 跑同样的输入样例。
7. 对比修复前后：
   - 风险分下降幅度。
   - 攻击成功率下降。
   - 拒答率是否过高。
   - 正常任务可用性是否受损。

### 前端展示

新增页面：

- `MitigationCenter.vue`：防护建议中心。
- `RegressionVerify.vue`：回归验证任务。
- `DefenseCompareReport.vue`：防护前后对比报告。

展示重点：

```text
修复前：
越狱成功率 42%，RAG 污染采纳率 35%，工具越权调用率 20%。

应用建议后：
越狱成功率 12%，RAG 污染采纳率 5%，工具越权调用率 0%。

同时正常任务通过率保持在 90% 以上。
```

## 11. 评价指标体系

建议围绕“发现能力、解释能力、防护能力、工程能力”四组指标设计。

### 11.1 风险发现能力

- RAG 污染采纳率。

- 报告生成成功率。

## 12. 比赛演示脚本

### 场景一：自适应红队攻击

1. 选择一个目标模型。
2. 选择风险类别，例如隐私泄露或有害内容。
3. 启动自适应红队。
4. 第一轮使用普通攻击，模型拒答。
5. 第二轮系统根据失败原因选择角色扮演或情景诱导。
6. 第三轮选择多轮上下文或编码混淆。
7. 平台展示攻击路径树、每轮得分和最终风险证据。

讲解重点：

> 固定模板只能测已知风险，自适应红队可以根据模型反馈持续探索未知弱点。

### 场景二：RAG 污染攻击

1. 导入正常政策文档。
2. 注入一条恶意污染文档。
3. 用户提出正常业务问题。
4. 系统检索时召回污染文档。
5. 模型输出被污染内容影响。
6. 平台定位风险来源是污染文档。
7. 系统建议启用可信分过滤、注入指令检测和引用约束。
8. 一键回归验证，污染采纳率下降。

讲解重点：

> 企业上线 RAG 应用时，安全风险不只在模型，还在知识库和检索链路。

### 场景三：Agent 工具越权

1. 配置模拟工具 `send_email_mock` 和 `query_user_profile`。
2. 外部文档中写入恶意指令，诱导 Agent 发送敏感资料。
3. Agent 计划调用高危工具。
4. 平台识别工具越权和敏感参数。
5. 策略引擎拦截调用。
6. 报告生成防护建议：工具白名单、参数校验、高危确认。

讲解重点：

> 当大模型拥有工具调用能力后，安全边界从“生成文本”扩展到“执行动作”，因此必须评测过度代理风险。

## 14. 与论文和前沿工作的对应关系

### OWASP Top 10 for LLM Applications 2025

对应风险：

- LLM01 Prompt Injection。
- LLM02 Sensitive Information Disclosure。
- LLM06 Excessive Agency。
- LLM07 System Prompt Leakage。
- LLM08 Vector and Embedding Weaknesses。

本项目落地方式：

- 提示注入和越狱由自适应红队覆盖。
- 敏感信息泄露由 JudgeService 和 TraceRisk 覆盖。
- 过度代理由 Agent 工具沙箱覆盖。
- 系统提示泄露由红队策略库覆盖。
- 向量与嵌入风险由 RAG 污染沙箱覆盖。

参考：

- https://genai.owasp.org/llm01/
- https://genai.owasp.org/llmrisk/llm08-excessive-agency/

### AgentDojo

AgentDojo 关注工具调用 Agent 中的不可信数据注入和安全测试。

本项目可借鉴：

- 将 Agent 工具调用放入可控沙箱。
- 为每个工具调用定义安全目标和失败条件。
- 记录攻击任务和正常任务之间的冲突。

参考：

- https://arxiv.org/abs/2406.13352

### PoisonedRAG

PoisonedRAG 说明 RAG 知识库是新的攻击面，少量污染文本即可操控回答。

本项目可借鉴：

- 构造污染文档。
- 统计污染召回率和污染采纳率。
- 对比防护前后的 RAG 鲁棒性。

参考：

- https://arxiv.org/abs/2402.07867

### StrongREJECT 和 JailbreakBench

这两项工作强调越狱评测需要标准化 benchmark、明确威胁模型和可靠裁判。

本项目可借鉴：

- 结构化保存测试样例。
- 统一评分字段。
- 把攻击成功率和正常任务可用性一起评估。
- 避免只看模型是否拒答，要看是否提供了可执行的有害信息。

参考：

- https://arxiv.org/abs/2402.10260
- https://arxiv.org/abs/2404.01318

### Many-shot Jailbreaking

Many-shot Jailbreaking 说明长上下文会带来新的攻击面。

本项目可借鉴：

- 在红队策略库中增加长上下文攻击策略。
- 检测模型是否被大量示例诱导改变安全边界。
- 将上下文长度、示例数量、攻击成功率作为实验变量。

参考：

- https://proceedings.neurips.cc/paper_files/paper/2024/hash/ea456e232efb72d261715e33ce25f208-Abstract-Conference.html

### Constitutional Classifiers

Anthropic 的 Constitutional Classifiers 和后续版本说明，自动红队数据、分类器防护、低误拒率是防御侧重要方向。

本项目可借鉴：

- 用红队失败和成功样例沉淀防护数据。
- 做输入、输出双侧风险检测。
- 在报告中同时展示风险降低和误拒率。

参考：

- https://www.anthropic.com/news/constitutional-classifiers
- https://www.anthropic.com/research/next-generation-constitutional-classifiers

## 15. 最终建议

比赛前最推荐的落地组合是：

```text
自适应红队 + Trace 风险归因 + 防护建议 + 回归验证
```

如果时间允许，再补：

```text
RAG 污染沙箱 + Agent 工具越权沙箱
```

不要优先做：

- 大规模多模态伪造检测。
- 联邦学习训练。
- 差分隐私训练。
- 完整知识图谱数据库。

这些方向适合写在远期规划和论文拓展里，但不适合作为当前工程的比赛 MVP。

最容易打动评委的不是“我们覆盖了很多方向”，而是：

> 我们能把一次安全问题从攻击生成、风险发现、链路归因、防护建议、回归验证到报告输出完整跑通，并且每一步都有工程实现和可视化证据。
